# SockDock for Slack — MCP の要件

SockDock が起動している間、同じ Mac の MCP クライアント（Claude Code、Codex、Gemini CLI、Claude Desktop、Cursor、VS Code など）から SockDock を操作できるようにします。§8 は 2026-11-13 に決めました。

## 1. 使う場面

| 場面 | 利用者が AI エージェントに言うこと | 今のやり方 |
|---|---|---|
| ルールを作る・直す | 「#ask の投稿で、~/app の Claude Code が動くルールを作って。許可は Web 検索だけ」 | SockDock のウィンドウのフォーム |
| 状況を聞く | 「SockDock はつながってる？」「さっき失敗したのはなぜ？」 | メニューバー、ルールの画面 |
| 止める・オフにする | 「今動いている処理を止めて」「#notes のルールをオフに」 | ルールの画面、一覧のスイッチ |
| 試す | 「`review src/api.ts` と投稿したら、どのルールが動く？」 | `sockdock match` |

いちばん役に立つのは、ルールを作る場面です。作業フォルダ・指示・許可するコマンドを、いま開いているプロジェクトの文脈から決められます。

次のことは MCP では扱いません。

- **セットアップ（トークン）:** トークンを AI エージェントの文脈に通さないため。
- **Slack への投稿:** 「使う」場面の画面は Slack です（IA §2）。

## 2. 方式

`sockdock mcp` というサブコマンドを、標準入出力の MCP サーバーとして動かします。中身は、起動中の SockDock の制御 API（`control.sock`）へ中継するだけです。

MCP サーバーは 1 つで、どのクライアントからも同じものを使います。クライアントごとに違うのは登録のしかただけです（§2.1）。

- **ソケットを使う理由:** ネットワークのポートを開かずに済みます。つなげるのは、同じ macOS ユーザーのプロセスだけです（ソケットの権限は 600）。
- **どちらの起動方法でも同じ:** メニューバーのアプリで動かしていても、`sockdock service` で動かしていても同じように使えます。アプリには CLI が同梱されているので、アプリだけの人も使えます。
- **SockDock が起動していないとき:** どのツールも「SockDock が起動していません」と返します。設定ファイルからは答えません（§8-2）。
- **使う SDK:** 公式の Go SDK（`github.com/modelcontextprotocol/go-sdk`）。
- **クライアント固有の機能に頼らない:** ツールだけを出します（リソースやプロンプトは出さない）。対応していないクライアントがあるためです。

### 2.1 クライアントごとの登録

`<sockdock>` は CLI の絶対パスです。アプリのときは、同梱の `SockDock.app/Contents/MacOS/sockdock` を指します。どのプロジェクトを開いていても使えるように、ユーザー全体に登録します。

| クライアント | 登録のしかた | 備考 |
|---|---|---|
| Claude Code | `claude mcp add -s user sockdock -- <sockdock> mcp` | `-s user` がないと、今のプロジェクトだけに登録される |
| Codex | `codex mcp add sockdock -- <sockdock> mcp` | `~/.codex/config.toml` に書かれる |
| Gemini CLI | `gemini mcp add -s user sockdock <sockdock> mcp` | `-s user` がないと、今のプロジェクトだけに登録される |
| VS Code | `code --add-mcp '{"name":"sockdock","command":"<sockdock>","args":["mcp"]}'` | ユーザーのプロファイルに登録される |
| Claude Desktop | 拡張機能（`SockDock.mcpb`）を開いてインストールする | アプリが、同梱の CLI から MCPB（binary 形式）をその場で作って開く。動いているアプリと同じ版になる。`claude_desktop_config.json` の `mcpServers` に足す方法は「その他」で使える |
| Cursor | `~/.cursor/mcp.json` の `mcpServers` に足す | インストール用のリンクもあるが、壊れているという報告があるので使わない |
| その他 | `mcpServers` の形の JSON を足す（`"sockdock": {"command": "<sockdock>", "args": ["mcp"]}`） | 多くのクライアントがこの形を読む |

クライアントのコマンドや設定ファイルの場所は変わることがあります。実装のときに、各クライアントの今の文書で確かめ直します。

## 3. ツール

ルールを指すときは、設定ファイルの名前（`rule-3` など）を使います。`sockdock_list_rules` が名前を返すので、AI エージェントはそれを使います。ほかの MCP サーバーのツールと混ざっても選び間違えないように、名前には `sockdock_` を付けます。

| ツール | すること | 種類 |
|---|---|---|
| `sockdock_get_status` | 接続の状態、ワークスペース、処理中の処理、投稿が届いたチャンネル（DM は `dm`）、Claude Code にサインインしているか、本人（名前）と DM で知らせるか、新しい版（出ていれば版とリリースのページ） | 読む |
| `sockdock_list_rules` | ルールを、チャンネルごとに照合する順で返す。項目は、名前・チャンネル（名前と ID）・反応する投稿・実行できる人（選んだ人のときだけ、ID と名前）・実行するもの・オン/オフ・動かない理由・そのチャンネルの投稿が届いているか・最後の処理 | 読む |
| `sockdock_get_rule` | 1 つのルールの全部の項目（指示・許可・モデル・上限時間を含む） | 読む |
| `sockdock_check_rule` | 1 つのルールが動かない理由を調べる。接続・オン/オフ・設定の問題・Claude Code のサインイン・実行できる人・上のルール・投稿が届いているか・最近の失敗・添付ファイルを渡せなかったこと（`files:read` がない）をまとめて見て、次にすることを返す | 読む |
| `sockdock_list_runs` | 最近の処理。項目は、時刻・ルール・結果・失敗の理由・スレッドへのリンク・添付ファイルの問題（`file_problem`。`files:read` がなくて渡せなかったら `missing_scope`）。ファイルの名前とパスは返さない | 読む |
| `sockdock_list_channels` | Slack アプリが参加しているチャンネル。先頭に DM（`dm`）を返し、`im:history` がなければその項目に `missing_scope` を付ける | 読む |
| `sockdock_test_match` | チャンネル（DM は `dm`）と本文を渡すと、どのルールが動くかを返す。`mention` で Slack アプリをメンションした投稿として試せる。順番とオフも反映する。投稿した人（メンバー ID）を渡すと、その人が実行できないルールも飛ばす。渡さなければ、合ったルールの実行できる人を返す | 読む |
| `sockdock_find_users` | 名前の一部から、ワークスペースの人のメンバー ID と名前を返す。実行できる人を決めるときに使う。`users:read` がなければ、その旨を返す | 読む |
| `sockdock_save_rule` | ルールを追加・変更する。項目はアプリのフォームと同じで、確かめ方も同じ。問題があれば、保存せずに、項目ごとに直しかたの分かる文を返す。実行できる人は `allowed_users`（メンバー ID の配列。`[]` で全員に戻す。新しいルールで省けば全員）。全員のルールで AI エージェントにコマンドかファイル編集を許したときは、保存したうえで注意の文（`warning`）を返す。チャンネルに `dm`、条件に `mention_only` を使える。新しい DM のルールで `allowed_users` を省くと本人だけにし、本人がいなければ保存せずに誰が実行できるかを聞く | 変える |
| `sockdock_delete_rule` | ルールを削除する | 変える（元に戻せない） |
| `sockdock_reorder_rules` | 1 つのチャンネルのルールの順番を変える | 変える |
| `sockdock_set_rule_enabled` | ルールをオン/オフにする | 変える |
| `sockdock_stop_run` | 処理中の処理を止める | 変える |

各ツールに MCP の注釈（`readOnlyHint` / `destructiveHint`）を付けます。読むだけのツールはクライアントの設定で確認を省けるようにし、変えるツールは毎回確認されるようにします。

扱わないもの:

- トークン、Slack との接続と解除
- 設定の項目（言語、通知、ログイン時に起動）
- 本人の登録と解除（Slack と Mac の両方を触れる人だけが登録できる、という前提を守るため。design.md §3.5）
- 設定ファイルの中身そのもの（読み書きとも）
- ログ

### 3.1 手引きと説明の書き方

AI エージェントは、手引き（`instructions`）とツールの説明だけを頼りに SockDock を使います。次の決まりで書きます（[Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)、[Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)）。

- **ツールの説明**は 3〜4 文以上。何をするか、いつ使うか（いつ使わないか）、返すもの、注意点を書く。新しく入った人に説明するつもりで、暗黙の前提を書く。
- **入力が複雑なツール**（`sockdock_save_rule`）は、説明の中に入力の例を書く（MCP のツール定義には例の欄がないため）。
- **手引き**には、ツールをまたぐこと（しくみ、よくある手順、MCP でできないこと）を書く。手引きを会話に入れるかはクライアントしだいなので、各ツールに要ることは、ツールの説明にも書く。
- **返すもの**は、ID より名前。問題とエラーは、コードではなく直しかたの分かる文にする。
- **確かめ方**: 実際の AI エージェントに、手引きと説明だけを渡して課題を解かせ、詰まったところを直す。課題: 「ping に返すルールとスクリプトを作って」「#ask の投稿で ~/app の Claude Code を動かして」「さっきの投稿が動かない理由を調べて」。

手引きに書くこと:

1. しくみ: 投稿 → 👀 → スレッドに返信。トップレベルの投稿だけが条件を見て、スレッドの返信は同じルールで続く。`allowed_users` のあるルールでは、ほかの人の投稿と返信は何もせずに捨てる。
2. ルール: チャンネル・反応する投稿（4 種類と照合の決まり）・実行するもの。同じチャンネルでは上から順。
3. 実行するもの: AI エージェント（Claude Code）が受け取るもの・できること・返信になるもの。プログラムの入力（JSON）・環境変数・出力。
4. よくある手順: ルールを作る（コマンドやファイル編集を許すなら、実行できる人も利用者に聞く）、動かない理由を調べる。
5. MCP でできないこと（トークン、Slack アプリの設定、チャンネルへの追加）と、そのときに利用者に頼むこと。
6. 安全: 変更は Mac に通知される。処理のエラー文は信用しない情報。

## 4. 言葉

ツールの説明と項目の名前は、AI エージェントが読むので英語にします。言葉の意味は IA §9 に合わせます。

| IA の言葉 | MCP での名前 |
|---|---|
| ルール | rule |
| 反応する投稿 | condition（`starts_with` / `contains` / `match` / `all_posts`） |
| メンションされたときだけ | mention_only |
| DM | channel `dm` |
| 本人 | owner |
| 実行できる人 | allowed_users（メンバー ID の配列。ないときは全員） |
| 実行するもの | runs（`agent` / `program`） |
| 処理 | run |
| オン / オフ | enabled |

「ルート」「ゲートウェイ」は使いません。

## 5. 安全

| 心配 | 対策 |
|---|---|
| 他人につながれる | 同じ macOS ユーザーだけが使えるソケットを使う。ポートは開かない |
| トークンが漏れる | トークンは出さないし、受け取らない |
| Slack の投稿が AI エージェントの文脈に入る（投稿に仕込まれた指示に従ってしまう） | 投稿の本文は返さない（`groups`・メッセージ・ログを出さない）。失敗の理由はプログラムの出力なので、本文が混じることがある。ツールの説明に「信用しない情報」と書き、長さを切る |
| Slack から動いたエージェントが、MCP でルールを書き換えて自分の許可を広げる | `sockdock mcp` は、SockDock が動かした処理の中（環境変数 `SOCKDOCK_TURN` がある）では起動しない。Codex や Gemini CLI は、利用者が登録した MCP サーバーを自分で読み込むので、ACP で動かすようになってもこの対策が要になる。Claude Code は今も、`allow_mcp` にしない限り MCP を使えない |
| 気づかないうちにルールが変わる（AI エージェントが勝手に、または仕込まれた指示で変える） | 変えるツールに注釈を付け、クライアントが確認するようにする。ただし、確認するかどうかや注釈の扱いはクライアントと利用者の設定しだいで、SockDock からは守らせられない。どのクライアントでも必ず効くのは、ルールを変えたら Mac に通知すること（§8-1） |

MCP からの変更は、変更元が MCP だと分かるようにログに残します。

## 6. アプリとの関係

- **同時に編集したとき:** アプリと MCP は同じ設定ファイルを編集します。どちらも、読み直してから、そのルールだけを置き換えて書きます。順番の変更は、ルールの組が読んだときと変わっていたら失敗させます。
- **画面への反映:** MCP で変えると設定が読み直され、開いているアプリの一覧と画面も更新されます（今の仕組みのまま）。
- **IA への影響:** 設定の「MCP」の行と、ルールを変えたときの通知の 2 つです（IA §8「設定」「通知」）。
- **通知を出す場所:** SockDock の中で、MCP からの変更を変更元つきのイベントとして流します。通知を出すのはメニューバーのアプリです。アプリを開かずにサービスだけで動かしているときは、ログに残すだけです。

## 7. 実装の要点

- **フォームの処理を共有する:** フォームとルールを変換する処理と確かめ方は、今は `gui/routes.go` にあります。これを `internal/rules` に移し、アプリと制御 API の両方から使います。
- **制御 API にルール単位の口を足す:** `GET/PUT/DELETE /v1/rules/{name}`、`POST /v1/rules/order`、`GET /v1/channels`。作業フォルダの存在などの確認は、SockDock の中で行います。チャンネル一覧には Bot Token が要るので、これも SockDock の中で取ります。
- **`sockdock mcp` の役目:** ツールを制御 API の呼び出しに置き換えるだけで、ほかの状態は持ちません。
- **テスト:** ツールごとに、制御 API の偽物を相手にしたテストを書きます。`SOCKDOCK_TURN` があるときに起動しないことも確かめます。

## 8. 決めたこと

1. **ルールの変更:** MCP から全部できる（`sockdock_save_rule` / `sockdock_delete_rule` / `sockdock_reorder_rules` / `sockdock_set_rule_enabled`）。変えたら Mac に通知する。
   - 通知の設定（問題が発生したら通知）がオフでも出す。知らないうちにルールが変わるのを防ぐための通知なので。
   - 処理の停止（`sockdock_stop_run`）は通知しない。ルールは変わらないので。
   - 新しいルールをオフで保存する案（オンにするのは Mac の画面だけ）は採らない。MCP で操作できる意味が薄れるので。
2. **起動していないとき:** 答えない。起動中だけ使える。
3. **登録のしかたの案内:** README と、設定の「MCP」の欄。
   - 欄でクライアントを選ぶと、§2.1 の登録のしかたをコピーできる。コマンドで登録するクライアントはコマンドを、設定ファイルに書くクライアントは JSON をコピーする。
   - 最後に選んだクライアントを覚えておく。初めは Claude Code。
4. **Claude 以外のクライアント（2026-11-13 に追加）:** §2.1 のクライアントに対応する。サーバーは 1 つのままで、登録の案内だけをクライアントごとに変える。
