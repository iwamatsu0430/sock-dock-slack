# すでにある Slack アプリでも使えるようにする — 設定情報の見せ方の検討（2026-11-13）

SockDock 専用に新しく作るアプリだけでなく、すでにある Slack アプリ（通知用のボットなど）でも使えるようにしたい。そのとき、Slack アプリに必要な設定を、画面にどう載せるかを検討する。結論は §5 の推奨。

## 1. 必要な設定と、SockDock が確かめられるか

新しく作るなら、作成ボタン（マニフェスト入り）で全部そろう。すでにあるアプリでは、利用者が Slack の管理画面でそろえる。

| 設定 | 値 | 何に使うか | SockDock が確かめられるか |
|---|---|---|---|
| Bot Token のスコープ | `channels:history` `groups:history` `chat:write` `reactions:write`（`channels:read` `groups:read` は任意） | 投稿を読む、返信する、👀、チャンネル一覧 | **できる**。`auth.test` の応答ヘッダー `x-oauth-scopes` に付いているスコープが並ぶ |
| App-Level Token のスコープ | `connections:write` | Slack とつなぐ | **できる**。つなげるかどうかで分かる（今も見分けている） |
| Socket Mode | オン | Slack とつなぐ | **ほぼできる**。オフだとつなげない（つなぐときのエラーで分かる） |
| イベントの購読 | `message.channels` `message.groups` | 投稿を受け取る | **できない**。どちらのトークンでも読めない |
| 2 つのトークンが同じアプリのもの | — | 受け取ったアプリで返信する | **できない**。Bot Token のアプリ ID は `users:read` がないと取れない |
| 設定を変えたあとの再インストール | — | 足したスコープを効かせる | スコープの確認で間接的に分かる |
| チャンネルへの追加 | — | そのチャンネルの投稿を受け取る | Bot Token 側は分かる（一覧に出る）。受け取る側は、投稿が届くかでしか分からない |

確かめられない 2 つ（イベント、同じアプリ）は、どちらも「つながるのに投稿が届かない」という同じ症状になる。今回の slacknewsbot の件は後者。

## 2. 設定情報を画面に載せることの課題と、なぜ課題か

| 課題 | なぜ課題か |
|---|---|
| **1. 大半の人には要らない** | 新しく作る人はボタンで全部そろう。全員に一覧を見せると、手順が長く難しそうに見え、やらなくてよい作業をしてしまう（段階的開示: よく使うものだけを最初に）。 |
| **2. 仕組みの言葉が並ぶ** | Socket Mode・イベント・スコープは SockDock の利用者の頭の中にない言葉（メンタルモデル）。意味が分からないまま書き写すことになり、間違えても気づけない。 |
| **3. 書いた場所と、設定する場所が離れている** | 設定するのは Slack の管理画面で、どの画面のどこかは Slack が変える（道順は書かない方針）。利用者は名前だけを頼りに探すので、SockDock の画面と行き来する。 |
| **4. そろったかを利用者が判断するしかない** | 一覧を見せても、SockDock からは一部しか確かめられない（§1）。チェックリストに✓を付けても、実際にそろっているとは限らず、「やったのに動かない」になる。言葉は SockDock が知っていることで作る原則（IA §5）とも合わない。 |
| **5. 新しく作るか、すでにあるものを使うかの判断を求める** | 1 つの画面に 2 つの道を並べると、自分がどちらかを先に決めなければならない（Choices）。今回は、判断の材料がないまま手持ちのアプリを選んでしまった。 |
| **6. すでにあるアプリを壊すおそれ** | Socket Mode をオンにすると、そのアプリのイベントは Socket Mode にだけ届き、それまでの Request URL（そのアプリ本来のサーバー）には届かなくなる。マニフェストを丸ごと貼ると、そのアプリの設定が上書きされる。通知用のボットが止まりうるので、黙って勧められない。 |
| **7. 同じアプリを別のプログラムも Socket Mode で使っていると、イベントが分かれる** | Slack は、同じアプリのつながりが複数あると、イベントをどれか 1 つに配る。SockDock と既存のプログラムで、投稿が取り合いになる。 |
| **8. 隠れた手順がある** | スコープやイベントを足したら、アプリを再インストールしないと効かない。一覧に載せても、この手順が抜けやすい。 |

課題 1〜5 は「見せ方」の問題、6〜8 は「すでにあるアプリを使うこと自体」のリスク。後者は、見せ方にかかわらず伝える必要がある。

## 3. 見せ方のパターン

| パターン | 中身 | 良い点 | 悪い点（§2 の課題） |
|---|---|---|---|
| **A. 一覧を常に出す** | 最初の画面に、必要な設定の表を出す（前回の案） | 1 か所で全部分かる | 1, 2, 4, 5。新しく作る人に負担 |
| **B. 道を選ばせる** | 最初に［新しく作る］［すでにある Slack アプリを使う］を選び、選んだほうの手順だけ出す | それぞれの道は短い。自分の状況を言葉で選べる | 5（選択が 1 つ増える）。選び間違えると遠回り |
| **C. 段階的開示（畳む）** | 新しく作る手順を出し、すでにあるアプリ向けは畳んだ入口の中に出す | 大半の人は短いまま | 入口の名前で伝わらないと開かれない（前回の「前に作ったアプリを使う」は伝わらなかった） |
| **D. マニフェストを渡す** | すでにあるアプリの「App Manifest」に足す部分を、コピーできる形で渡す | Slack の言葉そのまま。書き写し間違いがない | 6（上書きのおそれ）。YAML のどこに足すかは利用者が判断 |
| **E. つないでから、足りないものだけ出す** | 先にトークンを貼ってもらい、SockDock が確かめられるもの（スコープ、Socket Mode、`connections:write`）を確かめて、足りないものだけを出す | 一覧を読まなくてよい。SockDock が知っていることだけを言える（課題 4 を解く） | イベントと同じアプリは確かめられない（投稿が届くかで見るしかない） |
| **F. 困った場所で伝える** | 事前には何も出さず、投稿が届かないときにルールの画面で手がかりを出す（今の案） | いちばん少ない | すでにあるアプリを使う人が、試行錯誤することになる |
| **G. 外部の文書に任せる** | README の「すでにある Slack アプリを使う」へリンクする | アプリは短いまま。詳しく書ける | 画面を行き来する |

## 4. 組み合わせの考え方

- 課題 1・5 を避けるには、最初の画面の主役は「新しく作る」のままにし、すでにあるアプリの道は 2 番目に置く（C か B）。
- 課題 2・4 を避けるには、事前に一覧を読ませるより、つないだあとに SockDock が確かめて、足りないものだけを言う（E）。
- 確かめられない 2 つ（イベント、同じアプリ）は、E でも残る。項目として先に伝えたうえで、届かないときはルールの画面で手がかりを出す（F）。
- 課題 6・7 は、すでにあるアプリを使う道を選んだ人にだけ、1 文で伝える。

## 5. 推奨: C ＋ E ＋ F

**セットアップ 1**（新しく作る人には今と同じ）

- 主役は［api.slack.com で作る ↗］と、新しく作る手順の 3 行。
- その下に、入口を 1 つ置く（C）: 「すでにある Slack アプリを使う」。開くと次の 3 つだけを出す。
  - 必要な設定の名前（スコープ、イベント、Socket Mode）。どこで設定するかの道順は書かない。マニフェストの該当部分のコピーボタンを添える（D の良いところだけ）。
  - 注意 1 文: 「Socket Mode をオンにすると、このアプリのイベントは SockDock にだけ届くようになります。」（課題 6・7）
  - 「設定を変えたら、アプリを再インストールしてください。」（課題 8）

**セットアップ 2**（つないだあとに確かめる: E）

- 「Slack に接続」で、今の確認に加えて、Bot Token のスコープを `x-oauth-scopes` で確かめる。
- 必須のスコープが足りなければ、その欄の下に足りないスコープの名前を出して、ここで止める（どれを足すかが分かる）。
- 任意のスコープ（`channels:read` `groups:read`）が足りないだけなら、止めずに進む（チャンネル一覧の欄で、今までどおり伝える）。

**ルールの画面**（届かないとき: F）

- 今の案のまま。「このチャンネルの投稿は、まだ届いていません。」と、畳んだ「届かないとき」（このチャンネルに追加したか ／ 2 つのトークンが同じアプリか ／ イベントを購読しているか）。

この組み合わせだと、新しく作る人が読む量は増えない。すでにあるアプリを使う人は、入口で全体を知り、つないだときに足りないスコープを教えてもらい、届かないときは原因の候補を 3 つに絞れる。

## 6. 決めたこと（2026-11-13、すべて推奨どおり）

1. すでにあるアプリの入口は、畳む（C）。
2. 入口の中に、マニフェストの該当部分のコピーを付ける（上書きの心配がないよう「該当部分」だけ）。
3. 接続のとき、必須のスコープが足りなければ止める。任意のスコープだけが足りないなら進む。
