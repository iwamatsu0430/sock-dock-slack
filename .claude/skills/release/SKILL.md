# リリース

SockDock のリリースは、`v` で始まるタグを push すると GitHub Actions（`.github/workflows/release.yml`）が行う。アプリの zip を作って GitHub のリリースを公開し、Homebrew の tap（Formula と Cask）を更新する。このスキルの役目は、タグを作るところまでと、そのあとを見届けること。

リリースノートはファイルにしない。注釈付きのタグのメッセージに入れると、ワークフローがそれを GitHub のリリースの本文にする。アプリは新しい版を知らせるとき、この本文の利用者の言語の節をダイアログに出す（`.claude/tmp/design.md` §3.7）。

push は外に出る操作なので、必ず人の承認を得てから行う。

## 1. 前提を確かめる

次のどれかが満たされなければ、止めて人に伝える。

- `main` ブランチにいる（`git branch --show-current`）
- 作業ツリーがきれい（`git status --porcelain` が空）
- `origin/main` と同じ（`git fetch origin` のあと、`git status -sb` に ahead も behind もない）
- `mise run ci` が通る

## 2. 前の版からの差分を読む

```bash
prev=$(git describe --tags --abbrev=0 --match 'v*')
git log --no-merges --format='%h %s%n%b' "$prev"..HEAD
git diff --stat "$prev"..HEAD
```

コミットのメッセージだけで分からないものは、そのコミットの中身（`git show <hash>`）を読む。

## 3. メジャー・マイナー・パッチを判断する

Semantic Versioning 2.0.0 に従い、変更ごとに判断する。全体は、いちばん大きい変更に合わせる。

- **メジャー**: 互換性のない変更。設定ファイルを書き直さないと動かない、同じ設定でルールの動きが変わる、機能や CLI のコマンド・オプションがなくなる、プログラムに渡す JSON の形が変わる、など
- **マイナー**: 互換性を保ったまま、機能が増えた・変わった
- **パッチ**: 互換性を保ったままの直しだけ（バグの修正、文言、文書、ビルド）

0.x のあいだにメジャーと判断したときは、`0.(x+1).0` を提案し、`1.0.0` にするかを人に聞く。

## 4. リリースノートを書く

利用者に見える変化だけを書く。テスト、リファクタリング、開発用の道具、文書だけの変更は、利用者に関わるときだけ書く。

- 英語と日本語の両方を、同じ内容で書く。見出しは `## English` と `## 日本語` のちょうどこの形にする（アプリがこの見出しで節を選ぶ）
- 1 項目 1 行の箇条書き（`- `）。アプリが描くのは箇条書き・`` `コード` ``・`**太字**` だけなので、表・画像・入れ子の箇条書きは使わない。リンクは文字だけが出る
- 利用者がすることがある変更（Slack アプリのスコープを足して再インストールする、設定を書き換える）は、そのことを書く
- 日本語は英語の直訳にしない。画面の言葉（`.claude/tmp/ia.md` §9）と書き方（§7）に合わせる。例: 「Slack アプリへの DM でもルールを動かせるようになりました。」
- 全体で 10 行くらいまで。多ければ、まとめる

## 5. 人に確定してもらう

次を見せて、版とリリースノートを確定してもらう。

- 提案する版（例: `v0.1.1` → `v0.2.0`）
- 判断の一覧: 変更ごとに、メジャー・マイナー・パッチのどれと判断したかと、その理由
- リリースノート（英語と日本語）

直したいと言われたら直して、もう一度見せる。

## 6. タグを作って push する

リリースノートはスクラッチパッドのファイルに書き、タグのメッセージにする。1 行目はタグの題名、空行のあとに 2 つの節を書く。

```text
SockDock v0.2.0

## English
- Rules can react to DMs to the Slack app.

## 日本語
- Slack アプリへの DM でもルールを動かせるようになりました。
```

```bash
git tag -a v0.2.0 --cleanup=verbatim -F <ノートのファイル>
git tag -l --format='%(contents)' v0.2.0   # 中身を確かめる
```

`--cleanup=verbatim` を付けないと、git は `#` で始まる行をコメントとして消すので、`## English` と `## 日本語` の見出しがなくなる。中身を確かめるときは、2 つの見出しが残っていることを見る。

ここで push してよいかを人に聞き、承認を得てから push する。

```bash
git push origin v0.2.0
```

## 7. 見届けて報告する

```bash
gh run list --workflow=release.yml --limit 1
gh run watch <run-id>
gh release view v0.2.0 --json body,assets --jq '.body, .assets[].name'
```

次を確かめて報告する。

- ワークフローが成功した
- リリースの本文が、書いたリリースノート（2 つの節）になっている
- `SockDock-0.2.0.zip` と `checksums.txt` がある
- Homebrew の tap が更新された（`gh api repos/iwamatsu0430/homebrew-tap/commits --jq '.[0].commit.message'` が `sockdock 0.2.0`）

失敗したら、原因を調べて人に伝える。ワークフローは、Actions の画面の「Re-run failed jobs」で、公開済みのファイルを置き換えずにやり直せる。タグは、人に聞かずに消したり付け直したりしない。
